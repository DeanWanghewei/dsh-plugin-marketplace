# dsh-plugin-marketplace 设计与实施计划

## 一、设计依据（已在 deepseek-harness 源码中核实）

- harness 自带 `dsh plugin --profile <name> <pnpm args>`：以 profile 目录为 cwd 转发 pnpm（add/remove/update 均可），装完自动把声明了 `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}` 的包登记进 `dsh.profile.bundles`。spec 支持 npm 包名、`github:user/repo#ref`、`git+ssh://`、本地路径、tarball——**三种插件来源都可以委托它落地**。
- profile 的用户层 `$DSH_HOME/profiles/<name>/cordis.patch.yml` 会被运行中的 dsh **热监听**，安装/卸载后无需重启即生效；行内相对路径相对 profile 目录解析。
- `$DSH_HOME` 默认 `~/.dsh`（`DSH_HOME` 环境变量可覆盖）。
- pnpm ≥10 对 git 源的 `prepare` 脚本有 `allowBuilds` 门槛（首次 add 会失败并打印 key）——marketplace 需要识别并引导。
- `dsh --profile <name> --dump-config` 可不启动进程干跑校验合成结果。
- harness 内**没有**任何搜索/分类/市场工具——即本工程的空缺。

## 二、总体架构

pnpm + TypeScript(ESM, strict, Node≥20) monorepo，核心与外壳分离：

```
dsh-plugin-marketplace/
├── pnpm-workspace.yaml / tsconfig.base.json / .github/workflows/ci.yml
├── docs/                      # architecture.md / registry-schema.md / development.md
├── registry/default/registry.yaml   # 内置默认 registry（种子数据，zod 校验）
├── scripts/seed-from-harness.ts     # 扫描本地 harness checkout 生成种子条目
└── packages/
    ├── core/    # @dshm/core：领域模型、registry 加载/缓存、搜索、安装编排（无 UI 依赖）
    ├── cli/     # @dshm/cli：bin 名 dshm
    ├── server/  #（二期）@dshm/server：集中式 registry API
    └── admin/   #（二期）@dshm/admin：后台管理 Web UI
```

## 三、核心设计

### 1. 领域模型（`@dshm/core`，zod 校验）

```jsonc
// registry.yaml（schemaVersion: 1）
{
  "categories": [
    { "id": "agent-tool", "name": { "zh": "智能体工具", "en": "Agent Tool" }, "parent": null },
  ],
  "plugins": [
    {
      "id": "tool-cordis",
      "name": "DSH Cordis 工具集",
      "description": "模型侧运行时检查与动态包工具",
      "categories": ["agent-tool", "extension"], // 需求3：一插件多分类
      "tags": ["cordis", "tools"],
      "author": "deepseek-ai",
      "homepage": "...",
      "license": "MIT",
      "verified": true,
      "source": {
        "type": "path", // 判别式联合：npm | git | path
        "path": "/Users/deanwang/IdeaProjects/githubProject/deepseek-harness/packages/extensions/tool-cordis",
        "link": false, // true 时用 pnpm link:（开发期热改）
      },
      // "source": { "type": "npm", "package": "@deepseek-ai/dsh-tool-cordis" }
      // "source": { "type": "git", "url": "github:you/plugin | git+ssh://git@host/grp/repo",
      //             "ref": "<sha|branch>", "subdir": "packages/x", "private": true }
    },
  ],
}
```

### 2. 安装策略矩阵（`installer.ts`，委托现有机制，不自造轮子）

| source.type                       | 安装动作                                                                                                    | 卸载动作                              |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| npm / git / path(包目录)          | 构造 pnpm spec → `dsh plugin --profile P add <spec>`；git 的 subdir 情形先 clone 到托管目录再按本地路径 add | `dsh plugin --profile P remove <pkg>` |
| path(单文件插件，无 package.json) | 复制到 `$DSH_HOME/profiles/P/dshm/<id>/index.ts`，在 profile 的 `cordis.patch.yml` 追加托管块引用相对路径   | 删托管块 + 删目录                     |

`cordis.patch.yml` 托管块用 **marker 注释文本切片**（不做整体 YAML 重序列化，保留用户手写内容与格式）：

```yaml
# >>> dshm:hello-plugin
- insert:
    - id: hello-plugin
      name: ./dshm/hello-plugin/index.ts
# <<< dshm:hello-plugin
```

git 源安装遇到 pnpm `allowBuilds` 失败时：解析出 key，提示用户确认后（`--allow-build`）代写入 profile 的 `pnpm-workspace.yaml` 并重试——因为这一步等于"允许包在你的机器上执行构建脚本"，必须显式确认。

### 3. 本地状态与配置（`~/.dshm/`，`DSHM_HOME` 可覆盖）

- `config.yaml`：registry 列表（`{name, type: file|http, path|url, token}`）、默认 profile、per-host git https token（文件权限 600，**凭证永不进 registry 数据**）
- `store.json`：按 profile 记录已装插件、来源快照（版本/commit）、安装时间、触碰的文件——写入走 intent→commit 两阶段，可从中断恢复
- `cache/`：远端 registry 拉取缓存（带 TTL）

多 registry 共存：条目按 `registry:id` 命名空间防冲突，搜索按 registry 优先级合并。

### 4. CLI 命令面（一期全部实现）

```
dshm search <关键词> [--category a,b] [--tag t] [--registry r]   # 名称/描述/标签/分类过滤（多分类 OR）
dshm info <id>                                                    # 详情 + 已装状态
dshm install <id> [--profile P] [--ref v] [--link] [--yes]
dshm uninstall <id> [--profile P]
dshm list [--installed] [--profile P]
dshm categories                                                   # 分类树 + 每类插件数
dshm registry add|list|remove                                     # 管理本地/远端 registry 源
dshm doctor                                                       # 检查 dsh 可用性、$DSH_HOME、profile、pnpm
```

安装前后：展示摘要（来源/版本/分类/verified/license，git 源额外确认）；完成后提示 `dsh --profile P --dump-config` 干跑校验，并说明运行中的 profile 会热加载。

### 5. 私有 git 仓库支持（需求1）

- ssh 形式 `git+ssh://`：走本机 ssh-agent/密钥，零配置。
- https 形式：token 从 `~/.dshm/config.yaml` 的 per-host 配置注入（或依赖 git credential helper），不落 registry。
- 支持 `ref` 固定（默认建议 pin commit，防供应链漂移）、`subdir`（monorepo 内子包）。

### 6. 种子数据（`scripts/seed-from-harness.ts`）

扫描本地 harness checkout：`packages/**`（有 `dsh.bundle` 或插件导出的包）+ `examples/*`，生成 path 型条目；按目录规则预填分类（extensions→extension、含 defineTool→agent-tool、bundle→bundle、sdk→sdk、examples→example…）。第一天即有约 60 个真实插件可搜、可装、可验证全链路。

## 四、后台管理（需求2，二期实现、一期定死接口）

- **server**：Hono + better-sqlite3 + Drizzle（类型化 schema + 迁移）。公开 API：`GET /api/v1/plugins|plugins/:id|categories|search`；管理 API（Bearer token）：插件/分类 CRUD、`import/export`（与 registry.yaml 互转）、token 管理、审计日志。表：plugins、categories、plugin_categories（多对多）、api_tokens、audit_log。
- **admin**：React + Vite + Ant Design。页面：插件管理（CRUD + 多分类选择器 + 四种源类型表单 + verified/私有标记）、分类治理（增改合并，防分类膨胀）、registry 导入导出、token 管理、审计日志。
- 私有源凭证**不集中入库**：registry 只存 URL 与可见性；凭证留在各用户本地（cli 侧）或服务端 env。
- CLI 侧对接方式：`dshm registry add team https://<server> --token xxx`，一期的 registry 抽象（file|http）已预留。

## 五、工程规范（需求4）

- 分层：core 纯逻辑（dsh/pnpm 调用藏在 `Runner` 接口后，单测可注入假实现）；cli 只做参数解析与展示。
- vitest 单测覆盖：schema 校验、搜索过滤、spec 构造、patch 文本切片（含用户内容保留/幂等/卸载恢复）、store 两阶段写、installer 编排（假 Runner + 临时目录）。
- oxlint + prettier（与 harness 技术栈一致）、`tsc --noEmit`、tsup 构建、GitHub Actions CI（lint→typecheck→test→build）。
- changesets 版本管理 + conventional commits；docs/ 三篇文档（架构、registry 格式、开发指南）。

## 六、补充注意事项（需求5，我的追加）

1. **信任模型**：插件是任意 TS 代码且安装期构建即执行——git 源默认 pin ref、安装前显式确认、registry 的 verified/author/license 元数据透出。
2. **幂等与恢复**：重复 install 幂等；中断后 `store.json` intent 记录可清理半成品。
3. **不污染 harness**：只操作 `$DSH_HOME` 的 profile 层，绝不改 harness 源码 checkout。
4. **多 profile**：安装目标显式 `--profile`（默认可配），store 按 profile 隔离。
5. **分类元数据双语**（zh/en），与 harness 双语文档习惯一致，为 admin i18n 留路。
6. `dshm doctor` 把环境问题（无 dsh、无 pnpm、profile 不存在）挡在安装之前。

1. 脚手架：workspace、tsconfig、oxlint/prettier、CI、docs 骨架、git init。
